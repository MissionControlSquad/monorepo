# Plugins SDK & MCP — Parity Gap Analysis

## TL;DR

This domain is **two large, mature Paperclip subsystems** where our monorepo has a thin install-time
shell of one and **zero of the other**.

- **Plugin framework** — Paperclip ships a first-party, out-of-process **plugin runtime**:
  plugins are npm packages that run as *forked Node child processes* speaking JSON-RPC 2.0 over
  stdio, gated by a ~90-value **capability permission model**, with a rich `PluginContext` SDK
  (issues, agents, sessions, projects, db-namespace, secrets, events, jobs, webhooks, scoped API
  routes, managed agents/routines/skills, 15 UI extension slots, environment/sandbox drivers). It
  has a manifest+JSON-Schema config contract, a scaffolder (`create-paperclip-plugin`), a testing
  harness, hot lifecycle (install/enable/disable without restart), per-company enablement, dev
  hot-reload, and 10 example/real plugins. Our monorepo has an **install-time registry only**
  (validate manifest → store in `Plugin` table → admin UI toggles), with runtime **explicitly
  deferred** and capabilities "declared, not granted."
- **MCP** — Paperclip has a full **MCP Access Governance** platform (Apps v2): Paperclip acts as
  both an **MCP endpoint** (a stdio `@modelcontextprotocol/sdk` server exposing ~30 task/agent tools
  to Claude Code/IDEs, plus named HTTP **MCP gateways** with scoped tokens) **and an MCP gateway/proxy**
  that connects Paperclip agents to upstream third-party MCP servers (GitHub, Linear, …) through a
  policy engine: applications → connections (remote_http/local_stdio) → tool catalog with risk
  classification & quarantine → allow/deny **profiles** bound to agent/project/routine/issue/company
  → orthogonal **policies** (allow / block / require_approval / rate_limit / trust_rule) → human
  **action requests** → **audit** call-event log → supervised **runtime slots** with health, OAuth,
  redaction, and a 7-tab admin UI. **Our monorepo has literally none of this** — the only MCP
  reference is an `mcp-builder` agent-persona *template string*.

Net: **plugin registry is 🟡 (install-time only, no runtime); the entire plugin execution runtime is
❌; the entire MCP subsystem is ❌.** MCP is the single largest greenfield build in the parity effort.

### 1.2 Plugin gaps — monorepo implementation plan

Our registry (P3/P4/P21/P22) is a solid **install-time contract**; the gap is the entire **execution
runtime**. Recommended phasing — treat as a multi-epic effort; do **not** attempt full parity at once.

**Phase A — Runtime skeleton (worker isolation + RPC + capability gating).** *Size: L.*
- **Server:** add `apps/web/src/server/services/plugin-runtime/` — a `PluginWorkerManager` that
  `fork()`s a per-plugin child (mirror `plugin-worker-manager.ts`: minimal env, NDJSON JSON-RPC,
  crash backoff, SIGTERM→SIGKILL drain). Ship a `@mc/plugin-sdk` package (new `packages/plugin-sdk`)
  with `definePlugin`, a `PluginContext` factory, and the worker-side RPC loop.
- **Security/gating:** a `PluginCapabilityValidator` that maps each host-RPC method → required
  capability and rejects if the installed plugin's granted set omits it. **Change "declared → granted":**
  add an admin **grant** step (per-company `plugin_grants`) so install ≠ authorize.
- **Prisma:** `PluginProcess`/`PluginRuntimeStatus`, `PluginLog` (worker stderr capture), `PluginGrant`.
- **Tests:** worker spawn/crash/backoff, capability-denied path, env-leak assertion (no `DATABASE_URL`).

**Phase B — First useful capability slices.** *Size: L (split per slice).*
- Pick the highest-value host clients first: **state KV** (`plugin_state`), **scoped API routes**
  (`/api/plugins/:id/*`), **webhooks**, **jobs (cron scheduler)**, **http.outbound**, **secrets.resolve**
  (secret-ref indirection + vault). Each = a Prisma table (where stateful) + a host-RPC handler +
  capability + tests. **agent.tools.register** (P9) is the slice that bridges into MCP tool exposure —
  build it once the tool-invocation surface (Part 2) exists so plugin tools and MCP tools share one
  dispatcher.
- **UI:** manifest-declared **UI slots** (P13) require a host slot renderer + a `postMessage` bridge
  (`apps/web/src/views/plugin-slots/`). Start with `page` and `settingsPage` slots only. Treat plugin
  UI as trusted same-origin initially (match Paperclip's documented caveat) or invest in iframe
  sandboxing (larger).

**Phase C — Ecosystem & DX.** *Size: M.*
- Scaffolder (`create-mc-plugin`), SDK testing harness, dev hot-reload watcher, example plugins.
- Restricted DB namespace (P15) and managed resources (P16) are advanced — defer unless a concrete
  connector needs them.

**Sequencing note:** Phase A is a hard prerequisite for everything else and overlaps the MCP runtime
(both need a tool-invocation + audit spine). Build the **tool-invocation/audit core once** and let
both plugin-contributed tools and MCP-catalog tools flow through it.

**Gateway mode** = *Paperclip agents* call upstream MCP servers, fully governed. Mental model &

### 2.2 MCP implementation plan (greenfield)

This is a new **service domain**. Recommend an epic split so a first vertical slice ships before the
full governance stack. Order matters; each phase is independently valuable.

**Phase M0 — MCP client core (agents can call one upstream MCP).** *Size: M.*
- **Deps:** add `@modelcontextprotocol/sdk`.
- **Server:** `apps/web/src/server/services/mcp/` — a Streamable-HTTP client (port `mcp-http.ts`:
  `Accept: application/json, text/event-stream`, SSE-framed JSON-RPC) and an optional stdio client.
- **Prisma:** `McpApplication`, `McpConnection` (transport, config Json, credentialRefs, health).
- **Catalog:** `McpCatalogEntry` (name, inputSchema, riskLevel enum read/write/destructive, status,
  versionHash) + a `refreshCatalog(connectionId)` that calls `tools/list` and diffs.
- **Tool dispatch:** a `ToolInvocation` spine (`McpToolInvocation` table: actor/agent/issue,
  connectionId, toolName, argumentsHash, decision, latency) — **shared with plugin tools (P9)**.
- **Wiring to agents:** our agents run through a runtime adapter (`adapters.ts`) with on-disk context;
  the analog of Paperclip "writes adapter MCP config pointing at named gateway endpoints" is: generate
  an MCP config file into the agent workspace listing allowed connections + short-lived scoped tokens.
- **Tests:** catalog refresh diff, risk classification, a real `tools/call` round-trip (mock server).

**Phase M1 — Governance: profiles + policies + audit.** *Size: L.*
- **Prisma:** `McpProfile` (defaultAction deny), `McpProfileEntry` (selector/effect), `McpProfileBinding`
  (targetType agent/project/routine/issue/company, priority), `McpPolicy` (type allow/block/
  require_approval/rate_limit/trust_rule, selectors, conditions), `McpAuditEvent`, `McpRateLimitCounter`.
- **Server:** a decision engine (`evaluateToolAccess(actor, tool, args) → decision + reasonCode`)
  porting `tool-access-policy.ts` semantics: narrowest-scope binding precedence, **deny-beats-allow**,
  arg-hash-based trust rules. Every call writes an audit event; **audit-write failure must hard-fail
  the call** (control-plane incident, per runbook).
- **Security:** RBAC perms (`tools:admin/manage_connections/manage_profiles/view_audit/use`), redaction
  of all tokens/secrets in API responses, company_id tenant isolation on every query.
- **GraphQL:** queries `mcpConnections/mcpCatalog/mcpProfiles/mcpPolicies/mcpAuditEvents/mcpActionRequests`;
  mutations for connection/profile/policy CRUD, catalog refresh, health-check, approve/reject action.
- **Flags:** add `MCP` / `MCP_GATEWAY` keys to `packages/utils/src/feature-flag-keys.ts` (none exist today).
- **Tests:** allow/deny/approval/rate-limit decision matrix; binding precedence; tenant leakage.

**Phase M2 — Human approval + runtime slots + OAuth.** *Size: L.*
- `McpActionRequest` (signed, expiry) + approval UI card + trust-rule creation from an approval.
- `McpRuntimeSlot` supervisor for local_stdio (spawn/health/idle-evict/restart-storm suppression) —
  reuse the Phase-A `PluginWorkerManager` process-supervision patterns.
- OAuth-to-upstream (`McpOAuthState` with actor/session binding), stdio command templates.
- Runtime-health API + the 8 alert classes; secret store for `credentialRefs`.

**Phase M3 — Endpoint mode (Paperclip-as-MCP-server) + named gateways.** *Size: M–L.*
- A stdio `McpServer` (`packages/mc-mcp-server`) exposing our task/agent operations as tools
  (port `packages/mcp-server`), driven by a REST/GraphQL API client.
- Named HTTP **MCP gateways** (`McpGateway`, `McpGatewayToken` with token_hash/expiry/revoke, actions
  `tools/list`,`tools/call`) so IDEs/agents connect over authenticated HTTP with scoped tokens.

**UI (Phases M1–M3).** *Size: L.* New `apps/web/src/views/tools-access/` mirroring Paperclip's tabs:
Connections/Gateways, Profiles (+ wizard with a risk-aware tool picker), Policies, Audit, Runtime,
Paste-Config, Smoke-Lab. Gate behind an admin route + `tools:admin`.

### 2.3 Cross-cutting: unify plugin tools and MCP tools

Both plugin-contributed tools (P9) and MCP catalog tools terminate in the same conceptual pipe:
*actor requests a tool call → policy decision → (approval?) → execute → audit*. Build **one**
`ToolInvocation` + decision + audit core (Phase M0/M1) and register **both** sources into it, rather
than two parallel stacks. This is also how Paperclip's `plugin-tool-dispatcher.ts` and gateway share
the `ToolRunContext` type (`server/src/services/tool-gateway.ts` imports `ToolRunContext` from
`@paperclipai/plugin-sdk`).

**Bottom line:** the plugin registry is real but shallow (no runtime, capabilities not enforced);
MCP is a complete greenfield build and the largest single item in the parity backlog. Sequence them
around a **shared tool-invocation + audit core**, and ship a governed single-connection MCP vertical
slice (M0→M1) before attempting endpoint mode or full plugin execution.
