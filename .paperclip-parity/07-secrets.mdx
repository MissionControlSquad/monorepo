**Boundary:** buildbase owns human auth only. Everything below (secret storage, providers, resolution, MCP

**Legend:** ✅ present · 🟡 partial · ❌ missing · size S/M/L

> **Headline finding.** Two distinct domains sit behind this doc. (A) **Secrets** — we have a real Epic #5
> vault (`secrets_vault` flag) that is a genuine ~40% subset of Paperclip's: local AES-256-GCM envelope,
> versions, bindings, an access-event table, provider-config rows. What we lack is the **audited
> *runtime-resolution* path** (Paperclip never exposes a human plaintext reveal — see below), the
> **external providers** (aws/gcp/vault) as working resolvers, **user-scoped secrets**, **external-reference
> mode**, **projection classes**, and **rich per-consumer provenance**. (B) **MCP / access governance** —
> Paperclip has a large, production-grade tool-gateway (connections → catalog → profiles → policies →
> approvals → trust rules → audit) plus **low-trust presets**. We have **none of it (❌ across the board)**.
> This is the single biggest gap in the domain.

> **Important correction on "audited reveal".** Paperclip has **no human plaintext-reveal endpoint by design**.
> `doc/SECRETS-AWS-PROVIDER.md:404` explicitly says "Resolve the secret through a bound runtime path, not by
> adding a general-purpose reveal endpoint." Values are **write-only** to humans and only ever decrypted at
> **runtime for a bound consumer**, with every resolution written to `secret_access_events`. So the "audited
> reveal path we haven't built" is really the **audited runtime-resolution + access-event-on-read** path, not
> a reveal button. Our vault already matches Paperclip's *no-reveal* posture; what it's missing is the
> **audit-on-resolve** half. Recommendation: do **not** add a plaintext reveal UI — port the audited resolve path.

## Part A — Secrets

### A3. Runtime resolution + access-event audit (the "audited reveal" path)

Decrypt/resolve a secret value **only** for a bound consumer, and write an audit row on every read.

- **Paperclip:** `server/src/services/secrets.ts` `resolveSecretValueInternal:1008` → provider `resolveVersion`,
  updates `lastResolvedAt`, writes `recordAccessEvent:827` on **both success and failure** (`:1064`, `:1094`).
  Binding is enforced first: `assertBindingContext`/`assertBindingContext`-path throws
  "Secret is not bound to `<consumerType>`:`<consumerId>` at `<configPath>`" (`:805`). Public entry
  `resolveSecretValue:1118`; ephemeral probe-only path `resolveSecretValueForEphemeralAccess:1130` (gated to
  `system/environment-probe-config`, runs an authorization decision `secrets:read`). **No plaintext reveal
  route exists** — `server/src/routes/secrets.ts` never returns a value (grep of `value:` = write bodies only).
- **Ours:** 🟡 `resolveWorkspaceSecret:312` and `resolveEnvForAgent:424` and `getDecrypted:291` exist and
  return plaintext to server callers — but **write no access event** (docstring at `:306` explicitly says it
  does not go through an audited path). The audit table exists; enum actions `read`/`revealed`/`injected`
  (`secret.prisma:23`) are **defined but never written**. Only `created`/`rotated`/`bound`/`unbound` are
  recorded (`secrets.ts:118,277,372,397`).
- **Gap:** no audit-on-resolve, no binding enforcement at resolve time (any server caller can resolve any
  active secret by name), no failure-outcome audit, no `consumerType/consumerId/configPath` provenance on
  reads. **Size M** (see plan §P1 — highest priority).

## Implementation plan (monorepo)

Priority order. Each slice keeps the `secrets_vault` flag; add a new `mcp_access_governance` flag for Part B.

### P1 — Audited runtime-resolution path (Part A3/A4) — **do first, Size M**
1. **Prisma** (`secret.prisma`): widen `SecretAccessEvent` with `consumerType String`, `consumerId String`,
   `configPath String?`, `outcome String` (success|failure|missing|not_allowed|optional_omitted|provider_error),
   `errorCode String?`, `credentialOwnerId String?`, `responsibleUserId String?`, `issueId?`, `runId?`. Migration.
2. **Server** (`services/secrets.ts`): make `resolveWorkspaceSecret`/`resolveEnvForAgent`/`getDecrypted` require a
   `SecretConsumerContext { consumerType, consumerId, configPath?, actorType, actorId, issueId? }` and call a new
   `recordSecretAccess({ action: "read", outcome })` on **both success and failure** (mirror
   Paperclip `secrets.ts:1058-1108`). Enforce binding at resolve time — reject if no active binding matches
   `(consumerId, envVarName/configPath)`; write `outcome: "not_allowed"`.
3. **Security:** never log plaintext; keep no reveal endpoint (match Paperclip). Assert workspace isolation on
   every resolve.
4. **Tests:** unit — success writes `read` event; failure writes failure event; unbound consumer → `not_allowed`
   + throws; workspace mismatch → 403. Integration — agent run resolves env, audit rows appear with provenance.

### P2 — External providers (Part A2) — **Size L**
1. **Provider abstraction** (`services/secret-providers/`): port Paperclip's `SecretProviderModule` contract
   (`server/src/secrets/types.ts:127`) — `validateConfig/createSecret/createVersion/linkExternalSecret/
   resolveVersion/rotate/deleteOrArchive/healthCheck` + optional `listRemoteSecrets/discover`. Registry keyed by
   `SecretProviderKind`.
2. **Local provider:** wrap existing `secrets-crypto` as the `env`/local module (no behavior change).
3. **AWS provider:** port `aws-secrets-manager-provider.ts` (managed namespace `paperclip/{deployment}/{workspace}/
   {key}`, external-ref mode, KMS, tags, remote list/discover). Config from `SecretProviderConfig.config` +
   deployment env (`SECRETS_AWS_REGION/KMS_KEY_ID/...`), never store AWS creds in the vault (bootstrap trust model,
   `doc/SECRETS-AWS-PROVIDER.md:22`).
4. **Prisma:** add `externalRef`, `providerConfigId`, `providerMetadata`, `managedMode`
   (paperclip_managed|external_reference) to `Secret`; add `valueSha256`/`fingerprintSha256`/`providerVersionRef`
   to `SecretVersion`; write health fields on `SecretProviderConfig`.
5. **API/UI:** provider-vault CRUD + health check + remote-import preview (metadata-only) mutations; provider-vault
   management + import-from-vault UI cards.
6. **gcp/vault:** stub modules (validate + coming_soon health) mirroring `external-stub-providers.ts`.
7. **Tests:** provider health, managed create/rotate/resolve (SDK-mocked), external-ref resolve, import preview
   dedupe/conflict.

### P3 — Rich bindings + secret-ref model (Part A5) — **Size M**
Expand `SecretBinding` to 9 target types + dotted `configPath` + `versionSelector` + `projectionClass`; add
`secret_ref`/`user_secret_ref` env-binding union (`shared/types/secrets.ts:29` analog); port JSON-Schema
`secret-ref` path collection + adapter-config→binding sync. Add `tool_connection` target (prereq for Part B
credential brokering). Tests for precedence + projection-class gating.

### P4 — User-scoped secrets (Part A6) — **Size M**
Add `UserSecretDefinition` + `UserSecretDeclaration` models; per-user values as `Secret` rows with
`scope=user`+`ownerId`+`definitionId` (scope-shape CHECK); coverage query; self-serve set/rotate/delete (write-only);
definitions tab + my-secrets tab + missing-secrets banner UI.

### P5 — MCP / Access governance (Part B) — **Size L, largest** — behind `mcp_access_governance` flag
Sequence: (1) Prisma — the 23 tables (applications/connections/catalog/profiles/entries/bindings/policies/
gateways/tokens/invocations/action-requests/call-events/runtime-slots/rate-limit/audit). (2) Policy engine —
port `decide()` (allow/block/require_approval/rate_limit/trust_rule, deny-beats-allow, priority order) +
condition matcher + redaction. (3) Gateway runtime — session issuance, `tools/call` proxy with profile+policy
walk, action-request 409 + retry-with-`approvedActionRequestId`, trust-rule promotion (exact-hash), audit writer,
catalog changed-tool quarantine, credential injection via P3 `tool_connection` bindings + P1 audited resolve.
(4) Routes + GraphQL. (5) UI tabs (Applications/Connections/Profiles/Policies/Gateways/Runtime/Audit + profile
wizard + smoke lab). (6) Bundled safe-todo-kv example + smoke (allow-read / deny-write / audit-written).
**Security:** audit is append-only (no edit/delete); audit-write failure = incident; local-stdio fail-closed
unless trusted host; endpoint mode not policy-governed (document the boundary).

### P6 — Low-trust presets (Part B5) — **Size M–L**
Port `trust-policy.ts` presets + `resolveCoreTrustPreset` (intersect agent/project/issue/run policies, narrower
wins, fail-closed) + runtime containment (force sandbox + isolated workspace + binding-id-only secret refs, reject
inline sensitive env). Hook into our execution-policy + authorization layers. Depends on P3 (binding-id refs) and
our sandbox stack maturity.
